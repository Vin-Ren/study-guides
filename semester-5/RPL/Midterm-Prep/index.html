Foundation • Concept 1.1

What is Software? The Tripartite Entity & Dual Nature

Software is an engineered tripartite asset (Programs + Data Structures + Documentation) serving simultaneously as a product and as the vehicle delivering other products.
  • Instructions (Computer Programs): Executable code that delivers precise features, functions, and performance when run on target hardware.
  • Data Structures: Logical and physical memory representations that enable programs to manipulate, transform, and persist data accurately.
  • Documentation: Specifications, architectural models, user guides, and runbooks that govern operations, code intent, and long-term maintenance.
  • Dual Role as Product & Vehicle: Acts as a product delivering direct computing capability (apps, ERPs, firmware) and as a vehicle building/distributing other software (OS kernels, compilers, CASE tools, CI/CD pipelines).
Taxonomy • Concept 1.2

Software Application Domains

Software engineering is not one-size-fits-all; techniques vary drastically depending on operational domain constraints.
  • System Software: Operates at the hardware boundary (OS kernels, compilers, drivers), demanding low-level memory control and high concurrency.
  • Application Software: Automates business needs (ERP, inventory, payroll), where transactional data integrity and multi-user consistency dominate.
  • Engineering / Scientific Software: Numerical simulators (astronomy, stress analysis), prioritizing floating-point precision and compute throughput.
  • Embedded Software: Resides in digital microcontrollers (automotive ECUs, medical pumps), operating under hard real-time deadlines where late calculation is fatal.
  • WebApps & Mobile Apps: Globally distributed networks demanding zero-trust security, extreme elasticity, and responsive client UX.
  • AI & Data-Driven Software: Machine learning pipelines and non-deterministic models requiring probabilistic verification.
Failure Dynamics • Concept 1.3

The Failure Paradox: Hardware Bathtub Myth vs. Software Deterioration Reality

Hardware physically wears out over time; software does NOT wear out, but deteriorates because maintenance change side effects elevate the defect baseline.

Physical Hardware: Bathtub Curve

  • Engineered & Manufactured: Physical fabrication introduces material flaws, tooling tolerances, and assembly variances.
  • Infant Mortality (Burn-In Phase): High initial failure rates until manufacturing flaws are surfaced and repaired.
  • Useful Life Plateau: Low, steady-state failure rate during normal operational life.
  • Wear-Out Phase: Environmental stresses (friction, dust, thermal cycling, vibration) physically degrade components. Replacing worn parts with brand-new spares resets failure rate back down to baseline.

Software: Deterioration Curve

  • Engineered, NOT Manufactured: Duplicating binaries is cost-free and introduces zero physical variation. Quality problems stem from design errors.
  • No Moving Parts: Software has no friction and never rusts or mechanically fatigues.
  • Cumulative Maintenance Side Effects: Software must be updated for new OS versions, tax rules, and bug fixes. Each maintenance patch inadvertently injects unintended side effects into adjacent modules.
  • Elevated Defect Plateau: Repeated change spikes permanently elevate the baseline failure plateau until the software deteriorates into an unmaintainable legacy core.
Hardware Bathtub Curve (p. 7): Burn-in, steady-state plateau, physical wear-out.
Software Failure Curve (p. 8): Spikes from change side effects elevating baseline defect rate.
Engineering Stack • Concept 1.4

Pressman's Layered Technology

Tools sit at the top, automated by Methods, governed by Process, resting upon an organizational Quality Focus.
  • 1. Quality Focus (Bedrock): Total quality management (TQM) and continuous process improvement culture. Without quality, process becomes bureaucratic box-ticking.
  • 2. Process (The Glue): Defines framework activities, milestone gates, and schedule predictability; provides management control.
  • 3. Methods (Technical "How-To's"): Engineering practices for requirements gathering, analysis modeling, architectural design, TDD, and refactoring.
  • 4. Tools (Automated Support): CASE systems, IDEs, static linters, automated test runners, and CI/CD pipelines that automate methods and processes.

Essence of Practice • Concept 1.5

The Essence of Practice (Polya's 4 Steps & Questions)

Slide 1.1 p. 19–24 adapts George Polya's problem-solving framework into four operational stages with specific diagnostic questions.

1. Understand the Problem (Communication & Analysis - p. 20):

  • Stakeholders: Who has a stake in the solution to the problem?
  • Unknowns: What data, functions, and features are required to properly solve the problem?
  • Compartmentalization: Can the problem be partitioned into smaller problems that are easier to understand?
  • Graphical Representation: Can an analysis model (e.g. Use Case, DFD) be created?

2. Plan the Solution (Modeling & Software Design - p. 21):

  • Recognizable Patterns: Have you seen similar problems before? Is there existing software implementing the required data and functions?
  • Reusability: Has a similar problem been solved? Are elements of the solution reusable?
  • Subproblem Definition: Are solutions readily apparent for the subproblems?
  • Design Model: Can a design model (e.g. Class diagram, Package diagram) be created for effective implementation?

3. Carry Out the Plan (Code Generation - p. 22):

  • Conform to Plan: Does the solution conform to the plan? Is source code traceable to the design model?
  • Provably Correct: Has the design and code been reviewed through peer walkthroughs or correctness proofs?

4. Examine the Result (Testing & Quality Assurance - p. 23–24):

  • Testing Strategy: Is it possible to test each component? Has a reasonable testing strategy been implemented?
  • Validation: Does the solution produce results conforming to required data and functions? Has it been validated against all stakeholder requirements?
  • Sommerville's Focus (p. 24): The cost-effective development of high-quality software.

Hardware Bathtub Curve vs. Software Failure Curve

Case: An IT operations manager asserts: "Our 10-year-old banking COBOL core is experiencing more crashes this year because the software modules have physically worn out from handling millions of transactions, just like our hard drives."
Evaluate this statement. Explain the fundamental difference between the hardware bathtub curve and the software failure curve. Why does legacy software fail more frequently over time?
View Solution & Rubric
Step-by-Step Solution:

1. The manager's assertion is technically false. Software is a logical, not a physical element. It has no mechanical parts and cannot experience physical wear, friction, or thermal degradation.

2. Hardware follows the bathtub curve: initial burn-in defects drop to a low steady state, then spike when components physically wear out.

3. Software experiences a deterioration curve: when software is changed to adapt to new operating systems, business rules, or bug fixes, new defects are inevitably introduced as side effects. Over years, cumulative patches degrade the software's structural cohesion, raising the baseline defect rate.

Grading Rubric (10 Pts)

- Explaining hardware bathtub curve (3 pts)
- Explaining software deterioration due to change side effects (5 pts)
Common Mistake
Claiming that software crashes due to "memory wear". Memory hardware may wear out, but software failure spikes stem from cumulative change side effects.

Hierarchy • Concept 2.1

The Structure of a Software Process

A process organizes engineering effort into Activities (broad goals), Actions (deliverable sets), and Tasks (granular technical units).
  • Software Process: An adaptable framework providing structure, stability, control, and predictability across engineering teams.
  • Activity (Broad Objective): High-level lifecycle phases (Communication, Planning, Modeling, Construction, Deployment).
  • Action (Major Deliverable Set): Coordinated engineering tasks producing significant work products (e.g., Requirements Elicitation, Architectural Design).
  • Task (Granular Technical Work): Specific, immediate actions executed by engineers (e.g., conducting an interview, writing a unit test, validating a schema).
Governance • Concept 2.2

Umbrella Activities: Continuous Lifecycle Governance

Umbrella activities span the entire lifecycle continuously to govern risk, ensure quality, manage change, and track progress.
  • Tracking & Control: Compares actual engineering progress against schedule and budget baselines to trigger proactive corrections.
  • Risk Management: Systematically identifies, monitors, and mitigates technical and managerial hazards before they become crises.
  • SQA & Formal Technical Reviews (FTR): Peer walkthroughs and inspections that catch design flaws early when remediation costs are minimal.
  • Software Configuration Management (SCM): Governs version control (Git), branches, pull requests, builds, and change control boards.
  • Measurement & Metrics: Quantitative indicators (cyclomatic complexity, defect density, velocity) replacing subjective guesswork.
  • Reusability & Work Product Preparation: Harvests reusable patterns and ensures technical documentation is authored synchronously with code.
Communication Pathology • Concept 2.3

The Tree Swing Project: Why Process Discipline Matters

The Tree Swing cartoon dramatizes how unprincipled, siloed communication causes compounding disconnects between what is explained, designed, coded, billed, and actually needed.
  • The Core Lesson: Unprincipled ad-hoc projects fail not because programmers cannot code, but because roles operate in isolated silos without verified communication, modeling, and validation gates.
  • Customer Explanation: A 3-slat swing ≠ Project Leader Understanding: Tied around the trunk ≠ Analyst Design: Chopped tree with steel braces ≠ Programmer Code: Tied to the ground.
  • Commercial Disconnect: Documented as blank; billed as an executive roller coaster; installed as a bare rope; tree chopped down when supported.
  • The Real User Need: A simple tire swing suspended by a single rope from a sturdy branch—discoverable immediately through proper requirements elicitation!

Flow Topologies • Concept 2.5

Software Development Process Flows (The 4 Topologies)

A process flow describes how framework activities are chronologically sequenced: Linear (sequential), Iterative (repeated), Evolutionary (circular loops), or Parallel (concurrent).
Linear Flow (p. 21): Straight sequence from Communication to Deployment. Ideal for fixed, stable specs.
Iterative Flow (p. 22): Repeats activities before advancing. Solves technical unknowns.
Evolutionary Flow (p. 23): Circular loops delivering successive increments. Ideal for volatile requirements.
Parallel Flow (p. 24): Concurrent activities across decoupled sub-teams. Requires frozen API contracts.

Sequential • Concept 3.1

The Waterfall Model & The Late Integration Disaster

Linear sequential discipline (Communication → Planning → Modeling → Construction → Deployment) yields high administrative visibility but risks catastrophic late integration failures if requirements evolve.

Engineering Craft • Concept 4.4

Extreme Programming (XP) & The 12 Engineering Practices

XP supplies the technical coding craft that Scrum leaves out: TDD, Pair Programming, Continuous Integration, and Relentless Refactoring.

Created by Kent Beck, Extreme Programming (XP) takes beneficial software engineering practices and turns the dial up to "extreme" levels across four operational areas:

Planning: The Planning Game (user story cards estimated by developers and prioritized by customers) and Small Releases (frequent 1-2 week deployments).

Design: Simple Design (KISS) (design strictly for current stories, zero gold-plating), Relentless Refactoring (restructuring design without changing external behavior), and a shared System Metaphor.

Coding Craft: Test-Driven Development (TDD) (write automated unit tests before code), Pair Programming (Driver + Navigator at one workstation), and Collective Code Ownership (anyone can improve any line of code).

Integration: Continuous Integration (CI) (merge and test against mainline multiple times daily), Sustainable Pace (40-Hour Week) (banning overtime to prevent fatigue bugs), and an On-Site Customer.

Analysis Scope • Concept 5.1

The SDLC Analysis Phase: "What" vs. "How"

Analysis discovers "What" the system will do from the business domain perspective, leaving "How" (implementation design) for the Design Phase.

The Analysis Phase bridges stakeholder business problems and technical system design. Its fundamental objective is discovering, understanding, and documenting "What" the system will do, leaving technical implementation choices ("How") for the Design Phase.

A Requirements Definition is a formal statement of services and constraints. It serves multiple audiences: business users validate business goals, systems analysts model architectures, developers write code, and QA engineers author verification tests.

Taxonomy • Concept 5.2

Functional vs. Non-Functional Requirements (Dennis 4 Types + URPS+)

Functional requirements define processes and information; Non-Functional requirements define quality attributes (-ilities) categorized into Operational, Performance, Security, and Cultural/Political.

Functional: Specific processes the system must perform or information it must contain (e.g., "The system shall allow students to filter cooking classes by chef rating and seats").

Dennis's 4 Non-Functional Categories:
• Operational: Operating environment and integration (iOS/Android tablets; SAP ERP bridge).
• Performance: Speed, capacity, response latency (≤ 1.5s latency under 10k concurrent users).
• Security: Access control, authorization, encryption (RBAC salary access; bcrypt hashing).
• Cultural & Political: Multi-language locale, legal regulations (Indonesian OJK compliance, Rupiah formatting).

Larman's URPS+: Usability, Reliability, Performance, Supportability, plus auxiliary constraints.

Analysis Strategies • Concept 5.4

The Eight Requirements Analysis Strategies

Systematic analytical heuristics that transition as-is processes into optimized to-be requirements.

1. Root Cause Analysis: Focuses on causes rather than symptoms. Builds a cause-and-effect tree (5 Whys) until root causes are isolated.
2. Problem Analysis: Asks users to identify frustrations and proposed fixes (minor efficiency).
3. Duration Analysis: Compares task time to total elapsed cycle time. Large gaps indicate non-value-adding delays.
4. Activity-Based Costing (ABC): Calculates labor and material cost per step to find expensive bottlenecks.
5. Informal Benchmarking: Studies how leading competitors or other industries execute similar workflows.
6. Outcome Analysis: Focuses on what the customer fundamentally desires as the end value.
7. Technology Analysis: Explores how emerging tech (GPS, RFID, AI) can fundamentally transform processes.
8. Activity Elimination: "Force-fits" the elimination of each step to see if the workflow can survive without it.

Quality Criteria • Concept 5.5

Criteria of Good Requirement Definitions (The 8 Quality Dimensions)

Every requirement must be Correct, Unambiguous, Complete, Consistent, Verifiable (Testable), Modifiable, Traceable, and Ranked for Importance.

The 8 Quality Criteria:
• Correct: Accurately reflects stakeholder intent.
• Unambiguous: Has exactly one possible semantic interpretation. Avoid fuzzy words ("fast", "user-friendly").
• Complete: Includes all operational scenarios, constraints, and error behaviors.
• Consistent: Does not contradict other documented requirements.
• Verifiable (Testable): A finite test can objectively prove whether the system satisfies it.
• Modifiable: Structured with unique IDs so changes don't cause confusion.
• Traceable: Forward and backward links to design, code, and test cases (RTM).
• Ranked: Prioritized (MoSCoW) to guide trade-offs.

The Vague / Untestable Requirement Trap
Statements like "The system shall be user-friendly and fast" are worth 0 points on exams! Requirements must be quantified: "Any search query shall return results within 2.0 seconds for databases up to 1,000,000 records."

Elements • Concept 7.1

The Four Elements of a Data Flow Diagram

Process transforms data (Verb); Data Flow moves data (Noun); Data Store holds data at rest (Passive); External Entity defines scope boundary.
ElementGrammarSyntactic Invariants
1. ProcessAction Verb Phrase (e.g. 1.0 Validate Order)Must transform data. ≥ 1 input AND ≥ 1 output! Output must differ from input.
2. Data FlowNoun Phrase (e.g. Payment_Details)Data in motion. Must connect to at least one Process. Unidirectional arrow only.
3. Data StoreNoun Phrase ($D1, D2$)Data at rest. Must have ≥ 1 write and ≥ 1 read. Cannot talk directly to stores or entities!
4. External EntityNoun Phrase (e.g. Customer)External person, system, or organization defining scope boundary. ≥ 1 flow crossing boundary.
Decomposition • Concept 7.2

DFD Decomposition Hierarchy & Stopping Criteria

Context Diagram (Process 0, zero stores) → Level 0 DFD (3–7 major processes, stores appear) → Level 1 DFD → Functional Primitives.

Context Diagram: High-level system boundary view representing the whole system as Process 0. Shows all external entities and boundary flows. Rule: ZERO data stores appear on Context Diagrams!

Level 0 DFD: Decomposes Process 0 into major high-level business subsystems (Processes 1.0, 2.0, 3.0), internal data stores ($D1, D2$), and external entities. (Conventionally 3 to 7 processes).

Level 1 DFD & Functional Primitives: Decomposes an individual Level 0 process into child subprocesses. Decomposition terminates when a process reaches a functional primitive—simple enough to explain in a 1-page Structured English specification.

Validation • Concept 7.4

The Four Cardinal DFD Pathologies

Black Hole (input no output), Miracle (output no input), Grey Hole (insufficient input), and Illegal Direct Flows destroy DFD syntax validity.

1. Black Hole: Process with inputs but no outputs (information disappears).
2. Miracle: Process with outputs but no inputs (information generated from nothing).
3. Grey Hole: Process whose inputs are insufficient to produce its documented outputs.
4. Illegal Direct Flows:
• Entity → Entity: External conversation outside software scope.
• Store → Store: Tables cannot move data autonomously without a Process!
• Entity → Store: Users cannot write directly to DB without an application Process!

Balancing • Concept 7.5

The DFD Balancing Principle

Every data flow entering or leaving a parent process must appear crossing the boundary of its child decomposition diagram.

The Balancing Rule (Slide 07 p. 37): Every data flow, data store, and external entity crossing the boundary of Process $X$ on a higher-level DFD must appear on the lower-level DFD decomposing Process $X$. No data flows may magically appear or vanish across decomposition levels!

If a child diagram introduces an undeclared flow to a new entity, the system boundary is broken, requiring reconciliation of the parent Context Diagram and Level 0 DFD.

Analysis discovers "What" from the business perspective; Design specifies "How" for physical runtime environments, validated via formal peer walkthroughs.

Packages group related elements. Dependencies must be a Directed Acyclic Graph (DAG); beware the Architecture Sinkhole where trivial requests pass through all 5 layers with zero logic.
  • Acyclic Downward Dependencies: Packages in higher layers may import packages in lower layers. Lower layers (Data Management, Foundation) must NEVER import higher layers (Problem Domain, HCI). Zero circular cycles allowed.
  • Encapsulation Boundary: Problem Domain classes must remain pure business logic, knowing nothing of GUI buttons or SQL syntax.
  • The Architecture Sinkhole Anti-Pattern: Over-engineered layered systems where simple queries pass straight through all 5 layers without performing business logic, wasting latency and adding boilerplate. Remedies: Open Layering or CQRS query bypasses.

Coupling Generalization • Concept 10.5

Connascence: Strength, Degree & Locality

Two entities are connascent if a change in one requires a change in the other. Transform dynamic into static; weaken static (Meaning → Name via Enums); decrease connascence as distance increases!
  • Static Connascence (Source Code): Name (CoN) < Type (CoT) < Meaning (CoM: magic numbers) < Position (CoP: argument order) < Algorithm (CoA).
  • Dynamic Connascence (Runtime): Execution (CoE) < Timing (CoTi) < Value (CoV) < Identity (CoI: shared mutable reference).
  • The Three Golden Rules (p. 21): (1) Minimize overall strength (transform dynamic into static; weaken static via Enums); (2) Minimize across encapsulation boundaries; (3) Maximize within boundaries.
  • Bertrand Meyer Liability Theory: Precondition failure → Client (Caller) at fault; Postcondition / Invariant failure → Supplier (Callee) at fault.
Encapsulation (p. 20): Line (L0), Method (L1), Class (L2).
Rules (p. 21): Minimize across boundaries.

Design by Contract: Bertrand Meyer's Liability Theory

// Contract:
Precondition: sourceAccount.balance >= transferAmount AND transferAmount > 0
Postcondition: sourceAccount.balance == sourceAccount.balance@pre - transferAmount

View Solution & Rubric
Step-by-Step Solution:

1. Precondition Violation → Client (Caller) is at fault:

• If the caller passes a negative amount or attempts transfer with insufficient funds, the caller breached the contract. The supplier method has zero obligation to execute and must fail fast (throw IllegalArgumentException).

2. Postcondition / Invariant Violation → Supplier (Callee) is at fault:
• The postcondition is a guarantee delivered by the method author.
• If the caller satisfied all preconditions, but upon return the balance was deducted by the wrong amount or dropped below zero (violating invariant), the supplier method contains an internal coding bug.

3. Architectural Significance: DbC eliminates defensive programming clutter. Methods do not need redundant internal checks if preconditions are contractually enforced.

• Schedule rule: Departure time must be in the future when status is SCHEDULED.
Write formal Object Constraint Language (OCL) expressions declaring both class invariants on ScheduledFlight.

Step-by-Step Solution:
-- Context: ScheduledFlight Class Invariant (Slide 10 p. 40)
context ScheduledFlight
inv CapacityNotExceeded:
    self.bookings->select(b | b.status = BookingStatus::CONFIRMED)->size() <= self.aircraftCapacity

inv ValidFutureDeparture:
    self.status = FlightStatus::SCHEDULED implies self.departureTime > DateTime::now()

P10-11 Hard 20 Pts

Three Golden Rules of Connascence in Microservices

Case: Meilir Page-Jones and Dennis establish three rules for managing connascence across a system (Slide 10 p. 21):
1. Minimize overall connascence.
2. Minimize connascence across encapsulation boundaries.
3. Maximize connascence within encapsulation boundaries.
Apply these three rules to a distributed architecture. Why is Dynamic Connascence of Identity (CoI) permissible within a private in-memory method, but catastrophic across microservice boundaries?
View Solution & Rubric
Step-by-Step Solution:

1. Locality Principle of Connascence: As the distance between two components increases (from same method → same class → across packages → across microservices), connascence must be strictly weakened.

2. Connascence of Identity (CoI) within a Method: Within a single private method, two local pointer variables referring to the exact same mutable in-memory object is normal, high-performance, and safe because changes are encapsulated within a few lines of code.

3. CoI across Microservices is Catastrophic: Across microservices, Connascence of Identity means two autonomous services share a direct memory pointer or share the exact same mutable database table. This destroys service autonomy, causes distributed race conditions, forces locked-step deployments, and recreates a distributed monolith!

Grading Rubric (20 Pts)
8 pts for Locality Principle synthesis; 12 pts for contrasting CoI safety within private methods vs. distributed microservice disaster.
