L01

L01 — Introduction to Software Engineering

Source: Kuliah/RPL/1.1_Introduction_to_Software_Engineering.pdf (25 PDF pages). Its printed page numbers agree with PDF page numbers. The deck's central question is how to produce valuable, reliable software economically, rather than simply how to write code. [L01 pp. 3, 12, 24]

What counts as software, and what counts as an information system?

Software has three parts: executable instructions that supply functions and performance; data structures that let instructions represent and manipulate information; and documentation explaining operation and use. A program file alone is therefore an incomplete answer to “what is software?” Documentation includes what operators, maintainers, and users need to use it correctly. [L01 p. 5]

The slide's application categories are system software, application software, engineering/scientific software, embedded software, product-line software, web applications, and AI software. The categories describe where software is used, not mutually exclusive implementation technologies: an AI feature can be embedded in a web application. [L01 p. 9]

An information system (IS) uses software to create useful information or operational value for an organization. It is a narrower idea than software. A medical-records or tax-filing system is a natural IS example because its central job is handling organizational information; BIOS and an antivirus program illustrate software whose main purpose is different. The same type of IS may need different features in different organizations because goals and workflows differ. [L01 p. 10]

Distinction Question to ask Example
Software Are there instructions, data structures, and supporting documentation? Antivirus program.
Information system Does the software support an organization's information or business work? Clinic records and appointment workflow.
Computer science What computational theories and mechanisms make a solution possible? Data structures and algorithms.
Software engineering How do we apply systematic methods to a customer's real problem and maintain the solution economically? Requirements, design, implementation, and verification of the clinic system.

The computer-science/engineering relationship diagram places computer-science theories on one side, the customer's problem and desired functions on the other, and software-engineering tools and techniques between them. Refer to [L01 p. 11] to redraw it. A correct reading is that a technically elegant algorithm has little value if it addresses the wrong customer problem. [L01 pp. 11–13]

Why software behaves differently from hardware

Software is engineered/developed, not mass-manufactured in the classical sense: duplicating a finished executable is cheap, but discovering, designing, building, and changing it are costly. Components can be reused, yet much software still needs customer-specific work. These are characteristics of development economics, not claims that no physical media or assembly process is involved. [L01 p. 6]

The hardware “bathtub” failure curve falls after early manufacturing faults, stays low for a while, then rises as parts wear out. The software slide shows an idealized curve that falls as defects are removed and remains low. Its actual curve rises after changes and spikes when a change introduces side effects; software deteriorates through accumulated changes and defects, rather than physical abrasion. Study the two plotted curves and labeled axes at [L01 pp. 7–8]. A spike after release does not mean the code physically aged; it points to a defect or interaction introduced or exposed by a change. [L01 pp. 6–8]

The engineering response: systematic, economic, and quality focused

The deck gives both an early engineering definition—use sound principles to obtain reliable and efficient software economically—and the IEEE formulation: apply a systematic, disciplined, quantifiable approach to software development, operation, and maintenance, and study those approaches. “Operation and maintenance” belong in the definition; software engineering does not end when coding ends. “Quantifiable” means the work and its outcomes can be evaluated, not that every design decision has a precise number. [L01 p. 12]

The starting point is the problem. A complaint about a slow appointment process might be caused by staffing or approval rules, not merely by the absence of an app. First analyze the situation: decompose it into understandable parts and examine their relationships. Then synthesize a solution by combining parts that address the real constraints. Starting with a favorite technology and seeking a place to use it reverses this reasoning. [L01 pp. 13–14]

The layered-technology diagram at [L01 p. 15] is ordered from foundation upward: quality focus → process model → methods → tools. Quality focus is a pervasive concern. Process is the foundation that organizes work and management control, determines milestones and work products, gives methods their context, and manages change. Methods supply the technical “how” for communication, requirements analysis, design, construction, testing, and support. Tools automate or assist process and methods. A diagramming tool is not a development process; merely adopting it does not establish review criteria or ensure quality. [L01 pp. 15–17]

Layer Provides Example Common confusion
Quality focus Standard for evaluating outputs throughout the project Defect prevention and review Treating quality as a final test phase only.
Process Who does what, when, with which entry/exit criteria and products Iterative delivery cycle Treating the process as a programming language.
Method Technical technique for a task Requirements modeling or unit design Calling a tool a method.
Tool Automated or assisted execution UML editor or test runner Assuming automation fixes poor requirements.

The slide asks whether one can go straight to coding. One can, but trial-and-error success may be difficult to repeat and difficult to coordinate in professional work. The defensible exam answer is about repeatability, communication, quality, and change control, not “coding is forbidden before all documentation is complete.” [L01 p. 18]

Polya's four-step practice loop

The practice diagram at [L01 p. 19] maps a general problem-solving loop to software work:

flowchart LR
  A[Understand the problem<br/>communication + analysis] --> B[Plan a solution<br/>modeling + design]
  B --> C[Carry out the plan<br/>code generation]
  C --> D[Examine the result<br/>testing + quality assurance]
  D -- result exposes a gap --> A

Understand means identify stakeholders, unknowns, required data/functions/features, decomposable subproblems, and a possible analysis model. Plan means search for analogous solutions and reusable elements, solve subproblems, and represent the design so it can be implemented. Carry out means keep implementation traceable to design and review or prove component correctness where practical. Examine means test components, evaluate the testing strategy, compare actual behavior to required data/functions/features, and validate against stakeholder requirements. These are questions to ask, rather than four documents to produce once. [L01 pp. 19–23]

Verification versus validation: verification asks whether an implementation or intermediate product conforms to its specification/design; validation asks whether the delivered result satisfies stakeholder needs. The deck explicitly calls for design/code review in carrying out the plan and validation against stakeholder requirements when examining the result. A perfectly implemented but unwanted feature can pass verification and fail validation. [L01 pp. 22–23]

L02 — Generic Process Model

Source: Kuliah/RPL/02. Generic Process Model 1.2.pdf (25 PDF pages; printed numbers agree where shown). The deck separates what kinds of work are needed from how that work is arranged over time. [L02 pp. 12–24]

Process, life cycle, activity, action, and task

A process is a structured sequence of activities, actions, and tasks undertaken to make a work product. It answers who does what, when, and how toward a goal. It uses tools and techniques, resources under constraints, linked subprocesses, entry and exit criteria, principles, and intermediate/final products. A software development process is a framework for work needed to build high-quality software. When discussing a product from conception through implementation, delivery, use, and maintenance, the slides also call it a software life cycle. [L02 pp. 9–12]

An activity is a broad objective, such as communication with stakeholders. An action is a coherent set of tasks producing a major work product, such as architectural design. A task is a small, defined objective producing a tangible outcome, such as conducting a unit test. A unit test is therefore not a sixth framework activity, and “modeling” is too broad to be one small task. [L02 p. 13]

Activity: Modeling
  └─ Action: Architectural design
       ├─ Task: Identify a component boundary
       └─ Task: Review one interface contract

The slides say software engineering is creative and stepwise, usually involving many people. It is also iterative social learning: the knowledge gathered during the process becomes part of the product. That explains why a process helps when initial understanding is incomplete. The “Tree Swing Project” on pp. 4–6 depicts different interpretations of a swing, ending with a simple tire swing the customer needed; p. 7 makes the organizational lesson explicit: a polished system can fail if the team never learns how it serves organizational goals. [L02 pp. 4–8]

Five generic framework activities

These are Communication → Planning → Modeling → Construction → Deployment in the overview diagram at [L02 p. 14]. Every process model can arrange or repeat them differently. [L02 pp. 14, 20–23]

Activity Key work Typical output or decision Source
Communication Collaborate with customers and other stakeholders; discover objectives, features, functions, and requirements before technical assumptions harden. Shared problem/requirements understanding. [L02 p. 15]
Planning Define tasks, likely risks, required resources, expected work products, and schedule in a software project plan. A practical project “map” to guide and track work. [L02 p. 16]
Modeling Sketch requirements and design: architecture, components, and how they fit. Analysis/design models that expose missing or conflicting assumptions. [L02 p. 17]
Construction Generate code, manually or automatically, and test to uncover errors. Executable software plus test evidence. [L02 p. 18]
Deployment Deliver software, let the customer evaluate it, and collect feedback. Delivered increment and new knowledge for the next step. [L02 p. 19]

An exam scenario can span activities. For example, a customer review after deployment creates new communication work, which can change the plan and model. The names describe the purpose of work, not a rule that requirements may never change after construction. [L02 pp. 14–23]

Four process flows and process model qualities

Process flow specifies the sequence and timing of framework activities and their internal actions/tasks. Four diagrams show the contrast: linear and iterative on [L02 p. 21], evolutionary on [L02 p. 22], and parallel on [L02 p. 23]. [L02 p. 20]

Flow Diagram idea What changes from the previous flow Likely quiz cue
Linear C → P → M → Cn → D Activities follow one main path. Sequential stages and one eventual delivery.
Iterative Same path with feedback arrows to earlier work The team revisits an activity to revise its output. Testing reveals a design problem and modeling repeats.
Evolutionary An entire cycle returns from deployment/feedback to communication Repeated cycles produce successively more complete versions. A usable version leads to feedback and another version.
Parallel Some activities overlap on the timeline Work can proceed concurrently where dependencies allow. One part is being modeled while another is built.

Here C = Communication, P = Planning, M = Modeling, Cn = Construction, D = Deployment. Iterative and evolutionary both revisit work, but the [L02 p. 21] iterative diagram emphasizes local feedback links, whereas [L02 p. 22] explicitly loops through delivery to another development cycle. Parallel does not mean no coordination or that construction can precede its necessary design. [L02 pp. 21–23]

A software process model is an abstract view of a process from a particular perspective. A useful process should be visible (milestones/progress can be seen), understandable (activities and order clear), supportable (automation available where useful), and usable (accepted by developers). A process that looks rigorous on paper but cannot be performed by the team fails the last condition. [L02 p. 24]

L03 — Prescriptive Process Models

Source: Kuliah/RPL/03. Prescriptive Process Model-2025.pdf (49 PDF pages; printed numbers agree where shown). “Prescriptive” means a model supplies defined process elements and an expected workflow; the slides also call these conventional/traditional models. It does not mean that every prescriptive model is a purely linear waterfall. [L03 pp. 3–4]

Waterfall and its variants

Waterfall organizes communication, planning, modeling, construction, and deployment as a sequential path; the detailed boxes list requirements gathering, estimating/scheduling/tracking, analysis/design, code/test, and delivery/support/feedback. Redraw the canonical box chain from [L03 p. 6]. The slide states that feedback loops are possible in the proposed model, although mainstream use often treats it as strictly linear. Therefore “waterfall has no feedback under any circumstances” is an overstatement. [L03 pp. 5–6]

Waterfall fits most naturally when requirements are fixed and well understood from the start and work can proceed linearly. Its strengths in the slide are familiar engineering structure, early identification of requirements, visibility of stages, and limited requirements change. Its weaknesses are that projects rarely behave perfectly sequentially, changes are costly midstream, a working product arrives late, design must be specified before programming, and there is a long delay from analysis to delivery. For a changing, uncertain user interface, those weaknesses matter directly. [L03 pp. 7–8]

The V-shaped model pairs left-side development work with corresponding right-side assurance work. Read down the left and up the right at [L03 p. 9]: requirements modeling ↔ acceptance testing; architectural design ↔ system testing; component design ↔ integration testing; code generation ↔ unit testing. The diagram's links mean test planning can be traced to earlier specifications and designs. Unit tests target coded units; acceptance tests ask whether the system meets user requirements. Reversing the pairings is a common drawing error. [L03 p. 9]

The waterfall with prototyping variant inserts requirements and design prototypes into the staged process, helping validate/verify assumptions before later stages. The diagram at [L03 p. 10] also shows downstream unit/integration, system, and acceptance testing. The repeating previous stages variant at [L03 p. 11] shows how a discovered error or changed need forces earlier stage documents to be revised. Thus a feedback arrow is a cost of change and rework, not evidence that waterfall magically becomes a flexible evolutionary model. [L03 pp. 10–11]

Incremental and phased development

Incremental development delivers useful functionality in successive increments. In the slide's word-processor case, release 1 supplies basic text editing and file management, then release 2 adds styling. Each increment may use a small linear development path, while multiple parts or releases may overlap. The diagram at [L03 p. 13] shows staged increments; the phased-development diagram at [L03 p. 14] shows planning followed by repeated analysis/design/implementation leading to system versions 1, 2, and 3. [L03 pp. 12–14]

Select it when requirements are understood well enough to partition into subsystems and users need some capability quickly. Benefits: earlier useful deployment, easier feedback, and lower cost to accommodate changes. Risks: total process progress can be less visible and structure can degrade as increments accumulate unless architecture is maintained. Established bureaucracy can also make frequent releases hard to adopt. “Incremental” means each release adds usable scope, not merely that the same unfinished version is repeatedly redrawn. [L03 pp. 15–16]

Evolutionary development and prototyping

An evolutionary model expects the product to change over time: initial needs may be understood, but details and extensions remain uncertain, so iterations create increasingly complete software. The slides warn against treating this as identical to incremental development. A useful distinction is the dominant question: incremental planning partitions known features into delivered chunks; evolutionary work learns and revises uncertain details while the solution matures. Both may produce multiple versions, and a real project may use both ideas. [L03 p. 17]

A prototype is an initial system version used to demonstrate ideas, compare designs, and learn more about the problem and possible solutions. It is valuable when requirements are fuzzy because users can react to something concrete. It may be a stand-alone process or a technique inside another model, including the waterfall variant above. [L03 pp. 18, 10]

The Sommerville process at [L03 pp. 19–20] has four steps and four corresponding products: establish objectives → prototype plan; define functionality → outline definition; develop → executable prototype; evaluate → evaluation report. The objective and feature boundary matter because a prototype is an experiment: without specifying what it should teach, feedback is difficult to interpret. The Pressman loop at [L03 pp. 21–22] is communication → quick plan → quick design of user-visible aspects → construct prototype → deliver and obtain feedback → repeat. Quick design focuses on the part a user can inspect; it does not prove that the final architecture, security, or performance is complete. [L03 pp. 19–22]

Prototype approach What survives? Why choose it? Principal danger
Evolutionary/system prototyping A prototype may be refined into the actual system, shown in [L03 p. 23]. Feedback can directly steer successive versions. Shortcut design choices can become permanent.
Throwaway/design prototyping The experiment informs a later, separately designed system, shown in [L03 p. 24]. Learn about unknown requirements or designs without inheriting rough code. Stakeholders may mistake the demonstration for a nearly finished product.

The slides explicitly caution that rushed prototypes often compromise design, users may regard them as the final product, and rapid changes can be poorly documented. Advantages are clearer requirements and more visible progress; disadvantages include less comprehensive analysis and documentation difficulty. Set expectations about the prototype's purpose and fate before showing it. [L03 pp. 25–26]

Spiral: risk drives every loop

The spiral model represents software work as expanding loops, each loop a phase. Its defining feature is explicit risk management, not simply that it cycles. The Pressman spiral at [L03 p. 28] overlays communication, planning, modeling, construction, and deployment; the Sommerville diagram at [L03 p. 29] divides a loop into four quadrants: objective setting, risk assessment/reduction, development/validation, and planning. Study the diagrams directly if asked to draw the spiral; the particular sector labels differ between the two illustrations. [L03 pp. 27–29]

For each loop: (1) define objectives, constraints, and deliverable, and identify risks; (2) analyze the most important risks and reduce them through an appropriate experiment or decision; (3) choose a development/validation approach for that loop; (4) review results and plan whether/how to proceed. The first loop may produce a specification, a later loop a prototype, then progressively fuller software; plans are adjusted on every planning pass. A risk study is not an optional afterthought following all construction. [L03 pp. 30–32]

flowchart LR
  O[Set objective + constraints] --> R[Identify, analyze, reduce risks]
  R --> D[Develop + validate a chosen deliverable]
  D --> P[Review and plan next loop]
  P -- next loop: greater commitment --> O

Advantages: risks are visible and addressed, the model can span the software life cycle, and it can combine iterative/concurrent elements of other models. Costs: effective risk analysis needs expertise, and customers may need convincing that evolving work remains controllable. A loop without explicit risk assessment is iterative development, but misses the spiral model's defining control mechanism. [L03 p. 33]

Unified Process: phases, workflows, iterations, and views

The Unified Process (UP) is a tailorable framework associated in the slides with Jacobson, Booch, and Rumbaugh; examples of implementations are Rational Unified Process, OpenUP, and Agile Unified Process. Its defining characteristics are use-case driven, iterative and incremental, and architecture centric. Use cases describe user-visible behavior and help organize requirements; repeated iterations grow the product; architecture stays central as a structure for design decisions. [L03 pp. 34–36]

The architecture discussion distinguishes functional/external view (what users see the system do), structural/static view (classes, attributes, methods, relationships), and behavioral/dynamic view (object messages and state changes). The separate five-view diagram at [L03 p. 37] names use-case, logical, process, physical, and development views, with examples of diagram types: UseCaseD, ClassD/SequenceD/CommD, ActivityD, DeploymentD, and PackageD respectively. Do not collapse these two different classifications into one list. [L03 pp. 36–37]

The four UP phases describe changing project emphasis: Inception establishes business case, preliminary use cases and architecture, and an iterative plan; Elaboration understands the domain, expands use cases, creates an executable architectural baseline, reviews scope/schedule, and reduces major risk; Construction completes needed models and implements/tests increments (unit, integration, acceptance); Transition beta tests and delivers a documented system in its operational setting, including manuals and troubleshooting/install support. The phase illustration is at [L03 p. 38], and the phase descriptions/products at [L03 pp. 41–46]. The work-product table on p. 46 gives concrete artifacts: vision and initial business case in Inception; architecture, risk list, and refined models in Elaboration; software increment, tests, and support documents in Construction; delivered increment, beta reports, and feedback in Transition. [L03 pp. 38, 41–46]

UP workflows run across phases: six core workflows are business modeling, requirements, analysis/design, implementation, testing, and deployment; the three supporting workflows are configuration/change management, project management, and environment. The matrix at [L03 pp. 39–40] is essential: columns are phases subdivided into iterations, rows are workflows, and the colored band thickness indicates effort. Requirements and testing can occur in multiple phases; “Inception is only requirements” and “Transition is only deployment” misread the chart. [L03 pp. 39–40, 45]

UP term What it answers Example
Phase What lifecycle objective dominates now? Elaboration reduces architectural risk.
Iteration Which time-boxed cycle produces a reviewable increment? E2 within Elaboration.
Workflow What type of work is being done across time? Requirements or testing.
Work product What concrete result is produced? Use-case model or beta report.

The slide's UP best practices are develop iteratively, manage requirements, use component-based architectures, visually model software, verify quality, and control changes. These reinforce the phase/workflow matrix: change control and verification continue while versions grow. [L03 p. 47]

Selecting a process model from project conditions

The [L03 p. 48] Dennis decision matrix grades Waterfall, Parallel, Phased, Prototyping, Throwaway Prototyping, and XP against unclear requirements, unfamiliar technology, complexity, reliability, short schedule, and schedule visibility. It is a heuristic from the slide, not a mathematical rule. Its striking pattern is that throwaway prototyping scores excellent on unclear requirements, unfamiliar technology, complexity, and reliability, because it can investigate unknowns before the production build. Regular prototyping scores excellent for unclear requirements and a short schedule, but poorly for unfamiliar technology, complexity, and reliability. Phased development scores excellent for short schedules and schedule visibility. Waterfall scores poorly for unclear requirements and short schedules. [L03 p. 48]

Condition Strong candidates in slide matrix Reason to consider them
Unclear user requirements Prototyping, throwaway prototyping, XP Frequent user feedback or requirement experiment.
Unfamiliar technology or high complexity Throwaway prototyping Experiment and discard a risky technical design before production.
High reliability need Throwaway prototyping; also structured/phased models graded “good” Resolve unknowns while preserving deliberate production design.
Short schedule Phased, prototyping, XP Deliver useful capability or rapid feedback earlier.
Schedule visibility Phased or prototyping Visible versions/prototypes and checkpoints.

Why agile exists, and when to choose it

Agility is the ability to respond rapidly and appropriately to change. The deck makes it concrete through stakeholder communication, direct customer involvement, a team that controls its work, and frequent delivery of usable increments. The word agile describes this adaptive behavior, not merely short meetings or absence of documentation. [L04 p. 6, p. 9]

Question Plan-driven Agile
How is work organized? Separate process stages with defined outputs and formal handoffs. Requirements, design, implementation, and tests iterate together around working increments.
What happens to requirements? A specification is developed as an input to design; changes usually pass through formal control. Customer scenarios and feedback evolve alongside design and code.
When is it especially suitable? When complete advance analysis is essential, such as a safety-critical control system. When the environment changes quickly and customer involvement is available.

The contrast in the first two rows is the slide's process comparison; the fit examples are explicit on the preceding page. Neither approach forbids iteration. Plan-driven work can iterate within an activity; agile iterates across activities. [L04 p. 7–9] The cost-of-change illustration [L04 p. 12] is a motivation for early feedback and technical practices: as a change is discovered later, its repair can affect more dependent work. It is a conceptual curve, not a universal numerical law.

The manifesto prioritizes people and interaction, working software, collaboration with customers, and responding to change. Its closing qualification matters: processes, tools, documents, contracts, and plans still have value. The left side receives greater priority when a tradeoff is necessary. [L04 p. 10] Five summarized method principles are customer involvement, incremental delivery, recognition of team skill, embracing change, and simplicity. [L04 p. 11] The complete 12 principles add frequent delivery, daily business/developer cooperation, empowered people, effective conversation, working software as the progress measure, sustainable pace, technical excellence, minimal unnecessary work, self-organization, and periodic reflection. [L04 p. 13–15]

Human factors are part of the mechanism, not optional team decoration: competence, common focus, collaboration, ability to decide amid uncertainty, trust, respect, and self-organization let a short feedback loop work. [L04 p. 16] The slide's examples of agile fit are small or medium products and custom organizational systems with committed customers and few external regulations. [L04 p. 17]

Extreme Programming (XP)

XP couples small releases with engineering discipline. In planning, users describe goals as stories, developers estimate their cost, stories are grouped into an increment, and a delivery commitment is made. After the first increment, measured project velocity helps forecast later increments; it is an empirical planning measure, not a promise that every future story takes the same time. [L04 p. 21–22, p. 26]

In design, keep the solution simple (KISS), use Class–Responsibility–Collaboration cards to distribute responsibilities, build a spike as a small experiment for a hard technical question, and refactor code to improve internal structure while preserving behavior. [L04 p. 23] In coding, the slide places a unit test before code for a story and encourages pair programming. In testing, run unit tests daily, while customers define acceptance tests for visible behavior. Unit tests check small code units; acceptance tests ask whether the delivered behavior meets a business need. [L04 p. 25] For the process picture, revisit the XP activity loop [L04 p. 21], the release-cycle diagram [L04 p. 26], and the project map [L04 p. 27].

flowchart LR
  Story[Customer story] --> Estimate[Estimate and select increment]
  Estimate --> Test[Write unit test]
  Test --> Code[Pair-program solution]
  Code --> Refactor[Refactor]
  Refactor --> Accept[Customer acceptance test]
  Accept --> Feedback[Feedback and next story]
  Feedback --> Story

Scrum

The product backlog is the prioritized set of desired work, informed by customers and other stakeholders; the sprint backlog is the work selected for one fixed-length sprint. The deck says sprints normally last one to four weeks. At planning, the team reviews priority and risk and selects work. During the sprint it builds and tests; short daily meetings surface progress and obstacles. At its end, a review/demo presents the increment, then a retrospective evaluates how the team works before the next cycle. [L04 p. 30, p. 33–35]

Role or event Responsibility or decision Common confusion
Product Owner Defines and manages product-backlog/business direction; gathers customer and stakeholder input. [L04 p. 32] Does not replace the development team's technical work.
Development/Scrum Team Works together to deliver the software increment. [L04 p. 32] The deck stresses team collaboration rather than fixed internal roles.
Scrum Master Organizes the team and Scrum events. [L04 p. 32] Is not described as the product's business owner.
Sprint planning Chooses sprint work from the product backlog. [L04 p. 33] Product backlog and sprint backlog are not identical.

The larger Scrum life cycle has outline planning (objectives and architecture), repeated sprint cycles, and project closure (documentation/help and lessons learned). [L04 p. 31] The overview and sprint-cycle drawings are on [L04 p. 34–35]. L05 — Requirement Determination

Source: Kuliah/RPL/05. Requirement Determination.pdf, cited as L05.

Analysis, requirements, and readership

Requirements work turns an as-is system into a clear description of the to-be system. Analysis breaks the current whole into parts to understand their functions and relationships, identifies improvements, then defines what the proposed system must do. A requirement states required system behavior or a required characteristic; at analysis time it should express the business person's what, with design later specifying more of the how. [L05 p. 4–6]

The readers explain why the levels differ. Business/user requirements serve client managers, end users, client engineers, contractor managers, and architects; system requirements serve end users, client engineers, architects, and developers. A high-level promise and a buildable system rule can address the same need at different detail. See the readership map on [L05 p. 7].

Type Ask Examples and grading cue
Functional What process, information, or function must the system provide? “Record an application” or “store applicant grades.” It expresses required capability/data. [L05 p. 8]
Nonfunctional What quality, constraint, or property must the system satisfy? Response time, security restrictions, integration, portability, or cultural/regulatory fit. The slide groups examples as operational, performance, security, and cultural/political. [L05 p. 8, p. 32]

The requirements-engineering sequence is inception (problem and stakeholders), elicitation (discover needs), elaboration (model functions, behavior, and information), negotiation (priority, cost, risk), specification (document/models/scenarios/prototype), validation (check validity), and management (identify, control, track changes). These activities inform one another; the list is a process map, not proof that a requirement never changes after specification. [L05 p. 9–10]

flowchart LR
  A[As-is evidence] --> B[Elicit stakeholder needs]
  B --> C[Analyze causes and desired outcomes]
  C --> D[Specify to-be requirements]
  D --> E[Validate with stakeholders]
  E --> F[Manage changes and trace decisions]
  E -- gap or ambiguity --> B

Elicitation methods: choose based on the information gap

Writing and validating a good requirement

A strong requirement is correct, unambiguous, complete, consistent, verifiable, modifiable, traceable, and ranked for importance. [L05 p. 33] “Correct” needs stakeholder confirmation; “verifiable” needs an observable pass/fail condition; “traceable” needs an identifier and links to its source and later design/test. A requirement can pass one property and fail another.

The slide's bad unknown-source statement has two readings: does approval allow installing software from an unknown source or forbid it entirely? It is also phrased as a difficult-to-test negative and lacks an identifier. The proposed rewrite assigns an ID and states the positive gate: installation occurs only after testing and approval. [L05 p. 11] The “ASP” example is ambiguous until the acronym is expanded. [L05 p. 34] “Do not accept passwords over 15 characters” leaves three different behaviors possible: prevent extra typing, truncate silently, or show an error. Conceptual breakdown

Why a structural model exists

Functional models explain what happens: use cases show services visible to actors, while DFDs show movement and transformation of data. A structural model asks what domain facts must persist, and how those facts are related. DFD processes and stores can suggest classes, but they do not mechanically determine them. Model the domain first, then refine it with technology details in design. This iterative route reduces the semantic gap between a real business and its software representation. A shared vocabulary is a practical outcome: Pembelian must mean the same thing to users, analysts, and developers. [L08 pp. 5–10]

Model Main question Typical element Common mistake
Use case What goal can an actor achieve? Actor, use case Treating a use case as a stored class automatically.
DFD What data moves and how is it transformed? Process, flow, store Turning every flow into a class.
Class diagram What types of things and relationships are kept? Class, attribute, association Drawing a relationship whose link is never stored.
Object diagram What is one concrete snapshot? Named instance with values Using a class name without an instance or actual values.

A class is a template for objects; an object is one instance. An attribute records state about each instance, and an operation is behavior that the class can perform. For example, Penyewaan is a class, sewa-481:Penyewaan is an object, waktuKembaliAktual is an attribute, and hitungDenda() is an operation. A class diagram names types and constraints; an object diagram instantiates them with attribute values and links at one time. [L08 pp. 11, 23, 39]

Discovering classes and assigning responsibility

Read use-case descriptions for nouns that might be classes and verbs that might be operations, then challenge each candidate. A noun could be an attribute (alamat), an actor whose identity need not be stored, a temporary input, or a genuine domain class. Brainstorm physical things, incidents such as a payment, roles, interactions, and known patterns. Actors are candidates, not automatic classes; an actor generalization can suggest class generalization only when the corresponding persisted domain concepts have true “is a” semantics. Actors connected by use cases can suggest an association, but retain it only when the relationship matters to stored business facts. [L08 pp. 14–17, 45]

CRC means Class–Responsibility–Collaboration. “Knowing” responsibilities concern information an object owns; “doing” responsibilities concern work it performs. A collaborator is another object whose service is needed to fulfill a responsibility. The front card example contains class identity, description, associated use cases, responsibilities, and collaborators [L08 p. 20]; the reverse contains attributes and relationships [L08 p. 21]. Role-play a use-case scenario by handing a request to a card: if the card cannot answer without reaching into unrelated data, revise responsibilities or collaborators. [L08 pp. 18–21, 37]

Analysis, design, and quality

Analysis determines what the business needs. Design decides how the system will provide it. The transition is iterative: design may expose gaps in analysis and send the team back to refine a requirement. Conceptual breakdown

Object-orientation recap and design criteria

A class defines a type; an object is an instance. Abstraction keeps the essential domain properties; encapsulation groups state with behavior and restricts access; inheritance shares general features through a true subtype relation; polymorphism lets a common operation have subtype-specific behavior. These are the recap terms [L10 p. 4]. The deck evaluates designs chiefly through cohesion, coupling, and connascence [L10 p. 5].

Criterion Question Desired direction Example
Cohesion Does this class/method have one clear purpose? High Booking.calculateTotal() computes one booking's total.
Coupling How much does one module know or depend on another? Low, while still allowing necessary collaboration Pass only the needed booking ID rather than a large mutable object.
Connascence Will changing one element force a corresponding change elsewhere? Keep necessary dependence local; reduce cross-boundary dependence Hide storage format behind getPrice().

High cohesion and low coupling are related but distinct: a method can do one task while reaching through five other objects to do it. A class can also have many independent chores even if it calls no other class. [L10 pp. 6, 10, 19]

Class cohesion and method cohesion

The class-cohesion table runs from ideal through mixed-role, mixed-domain, to mixed-instance [L10 p. 7]. Ideal means members all support one concept. Mixed-role means a domain class carries attributes representing objects at its same layer that do not belong to its own semantics. Mixed-domain means a domain class also contains facts from another architectural layer, e.g., a network port field inside Customer. Mixed-instance means one class really describes two different object types and should be split. These labels and ordering are important because a question may ask which kind of cohesion defect is present, not just whether cohesion is low.

The slide's Flight example [L10 p. 8] starts with flight number and departure/arrival schedule alongside departure/arrival airport names. Split out Airport(name, location), then link Flight to departure and arrival airport roles. This gives airport facts one owner and avoids names repeated on each flight. Preserve two distinct role names even though both ends have type Airport; otherwise you cannot distinguish origin from destination.

The method-cohesion ladder on [L10 p. 9] is, from good to bad:

The ordering is the slide's grading taxonomy; in real code, a small sequential or communicational method can be sensible. The exam distinction is why the operations belong together. [L10 pp. 6, 9]

Interaction coupling and the Law of Demeter

Coupling measures dependency between classes, objects, or methods; in this deck, interaction coupling is the effect of message passing (method calls). High coupling makes change propagation and reuse harder. The table [L10 p. 11] orders these types from better to worse:

Type What crosses the boundary Why it matters
No direct coupling Nothing; methods do not call each other. Fewest direct dependencies, though this is not a goal when collaboration is needed.
Data Needed simple value, or an entire passed object truly needed by callee. Callee receives exactly useful information.
Stamp A whole composite object is passed but only a small part is used. Callee becomes dependent on a broad structure.
Control Caller passes a flag that determines callee's internal branch. Caller reaches into how callee works.
Common/global Both use shared global data. Hidden shared state ties changes together.
Content/pathological One object method accesses another object's hidden internals. Breaks encapsulation and information hiding.

The ScheduledFlight example asks where countTotalBooking() belongs [L10 p. 12]. Put it with ScheduledFlight (or a dedicated booking collection/repository attached to that flight at implementation time): it counts bookings for one scheduled flight. Placing it on a single Booking makes one booking responsible for finding all its peers, increasing coupling. Flight is the general route/schedule definition, not a dated flight instance, so it also lacks the right scope. If the design lacks a navigable booking collection, add the required association/service explicitly instead of making the method magically scan all bookings.

The Law of Demeter permits a method to call itself, objects held directly in its attributes (including inherited attributes), parameters passed to it, objects it creates, and in the deck's formulation, a globally stored object. [L10 p. 13] The design intuition is “talk to your immediate collaborators.” The classic violation is post.sale.payment().amountTendered(): post first obtains a Payment from Sale, then talks to that returned object, whose type and behavior post now knows. Prefer sale.paymentAmount() and let Sale call its Payment; see the paired communication/class diagrams [L10 pp. 14–17]. The method call chain adds a little forwarding overhead but reduces interclass knowledge and increases robustness [L10 p. 18]. This is a heuristic: do not add meaningless forwarding methods when direct collaboration is part of the intended interface.

Connascence: change that must travel together

Two modules are connascent when changing one is likely to require a corresponding change in the other. The deck distinguishes level 0 (within a line), level 1 (within a method), and level 2 (inside a class) encapsulation [L10 pp. 19–20]. Keep unavoidable mutual knowledge inside a small boundary and minimize it across method/class boundaries; eliminate unnecessary dependence overall [L10 p. 21]. Direct subclass access to hidden superclass details is a warning sign: a superclass change then forces subclass edits [L10 p. 22].

Connascence type Shared assumption Example of forced paired change
Name A member has a particular identifier. Rename price and update its references.
Type/class A member has a particular type. Change int to Money; callers/declaring class adapt.
Convention Values carry an agreed meaning. Change account-number range/encoding; every interpreter adapts.
Algorithm Two operations must use compatible procedures. Change data structure ordering; insert and lookup both adapt.
Position Order is significant. Reorder positional arguments or statement sequence; caller/callee adapt.

These are the five types pictured on [L10 p. 23]. A method that receives (startDate, endDate) without names at call sites has position dependence; a DateRange value can localize it. Do not treat every dependency as a bug: a public method name is necessarily shared, but a stable interface prevents internal changes from spreading.

Five object-design activities

The deck's sequence is (1) add specifications, (2) identify reuse, (3) restructure, (4) optimize, (5) map domain classes to the implementation language [L10 p. 25].

  1. Add specifications: review for necessary and sufficient classes, missing/extraneous attributes or methods, and appropriate visibility [L10 p. 26]. Choose each method's signature: name, parameters, and return type [L10 p. 27]. Define preconditions, postconditions, invariants, and violation/exception handling [L10 p. 28].
  2. Identify reuse: a pattern is a reusable design idea; a framework is a domain-oriented implemented class structure; a class library supplies reusable implemented classes; a component is a pluggable encapsulated software unit. Add any concrete, language-specific classes introduced by reuse to the design diagram. [L10 p. 29] The examples are Whole–Part for aggregate/composite structure [L10 p. 30], Command–Processor to separate command interface from the actual supplier/executor [L10 p. 31], and Forwarder–Receiver for peer-to-peer communication [L10 p. 32].
  3. Restructure: factor crosscutting aspects into a separate method/class; normalize relationships into implementable attributes/references and turn association classes into regular design classes; verify each inheritance arrow truly means specialization. [L10 pp. 33–34] “Convert association to attributes” here is a design mapping to navigable references or collections, not permission to duplicate every related object's descriptive fields in the earlier analysis model. For example, Order.customer: Customer represents the association, while copying customerName into every order would be a separate snapshot requirement.
  4. Optimize: examine frequent/long message paths and attribute access; consider derived/cached values and triggers to avoid repeated calculation; evaluate collapsing one-to-one classes when their separation has no purpose. Review direct and indirect method fan-out and reorder frequent filtering steps to reduce work. Balance speed against clarity. [L10 pp. 35–36]
  5. Map to language: choose representation according to the language's inheritance support: single inheritance, object-based without inheritance, or traditional procedural language. The last is marked less desirable for direct object mapping on the slide. [L10 p. 37]

L06 — Functional Modeling

L07 — Process Modeling

  • DFD processes need verb + noun labels; data flows, stores, and external entities take nouns. Avoid an action label such as Send Data on a data arrow. [L07 p. 8–11]

L08 — Structural Modeling with Class Diagrams

  • Storage rule: a class asserts its object data is retained; an association asserts the specific link is retained. Process participation alone is insufficient. [L08 p. 45]
  • No duplicate analysis attributes: follow a relationship to the owner of the fact, e.g., doctor's name on Dokter, rather than copy it onto appointments. [L08 p. 45]
  • Context determines ownership: isKoordinator and stock quantity are properties of particular pairings, not global properties of one endpoint. [L08 pp. 42, 47]
  • Multiplicity belongs at the target end: answer “how many target objects for one object at the other end?” before writing either number. [L08 pp. 27–29]
  • Scope changes lower bounds: “may” normally permits zero, while “every confirmed purchase has one or more payments” supports a 1..* payment end. [L08 pp. 41, 43]
  • Strong relationship symbols need strong meaning: hollow diamond = independent part; filled diamond = lifecycle ownership; hollow triangle = superclass. [L08 pp. 31–34]
  • Association class requires link-specific attributes. A many-to-many relation alone does not force one. [L08 p. 30; L09 p. 12]

L09 — Moving Into Design

  • Verification versus fidelity: legal UML syntax cannot establish that multiplicities or flow order match reality. [L09 pp. 8, 10–12]
  • Walkthroughs detect and record first; edits follow afterward. Do not describe the meeting as a live redesign session. [L09 p. 8]
  • One-to-one mapping applies to diagrammed use cases and their specifications, not actors to use cases. [L09 p. 10]
  • CRC collaborators imply relationships but do not automatically determine whether the relation is aggregation, composition, or a plain association. [L09 pp. 11–12]
  • A class-typed attribute implies a relationship; a primitive/string field does not by itself demand a class link. [L09 p. 12]
  • Analysis asks what; design adds how and the environment. Architectural, class, interface, and component designs are complementary. [L09 pp. 4, 14–19]
  • Partition, layer, and package are different decisions. A package is a grouping notation; a layer has a responsibility/dependency role. [L09 pp. 22–28]
  • Strategy choice uses all table criteria. “Package is fastest” does not make it suitable when function or integration fit is unacceptable. [L09 pp. 31, 34–35]
L10

L10 — Class and Method Design

  • Cohesion is internal focus; coupling is external dependence; connascence is paired-change pressure. They are related metrics, not synonyms. [L10 pp. 5–6, 10, 19]
  • Recognize the exact table labels. Mixed-role/mixed-domain/mixed-instance are class cohesion defects [L10 p. 7]; functional through coincidental are method cohesion levels [L10 p. 9].
  • Stamp versus data coupling: passing an object whose full interface is needed is data coupling in this deck; passing the whole object to read only one field is stamp coupling. [L10 p. 11]
  • Control coupling passes a flag that chooses callee behavior; a normal domain value used in a calculation is not automatically a control flag. [L10 p. 11]
  • Law of Demeter “friend” scope is per method call. A returned object reached through an allowed collaborator is not automatically allowed. Memorize the POST–Sale–Payment diagrams [L10 pp. 13–17].
  • Keep change dependence local. A subclass poking into superclass internals magnifies cross-class connascence even if the language permits it. [L10 pp. 21–23]
  • Analysis normalization and design mapping occur at different levels: class references implement associations; duplicating names/attributes creates another fact and needs a requirement. [L08 p. 45; L10 pp. 33–34]
  • Pre, post, invariant: before call, after successful call, always in valid states. A contract describes a public method agreement; method specification includes implementation guidance. [L10 pp. 39–46]
  • Optimization has a clarity cost. Caching derived values, collapsing classes, or reducing fan-out must preserve domain meaning and maintainability. [L10 pp. 35–36]

Question 01Software engineeringL01 pp. 6–8

A deployed program works initially, then each hurried maintenance change causes new defects. Which explanation best matches the lecture's software failure curve?

Answer: B

Software does not wear physically. The curve illustrates how changes can introduce side effects and cause defect spikes; disciplined maintenance can reduce that effect. A clean initial release and a constant rate are not implied.

Question 02Software engineeringL01 pp. 15–17

A team buys sophisticated test and deployment tools but has no shared workflow or quality practices. Which layer is most directly missing beneath the tools?

Answer: B

In the layered technology diagram, quality focus supports process; process organizes methods; tools support those methods. A tool purchase cannot supply the missing underlying practice.

Question 03Problem solvingL01 pp. 19–23

Before coding a clinic system, the team identifies stakeholders, missing information, and constraints. Which Polya-inspired step is it performing?

Answer: A

Questions about stakeholders, unknowns, and constraints belong to understanding the problem. Carrying out and examining occur after a solution plan exists; deployment is a separate lifecycle activity.

Question 04Process frameworkL02 pp. 13–19

Which ordering follows the five generic framework activities?

Answer: B

The framework names communication, planning, modeling, construction, and deployment in that sequence. Iterations may revisit activities, but that does not change their names or the conceptual flow.

Question 05Process modelsL03 pp. 5–9

A team wants every development stage paired with a corresponding test level planned early. Which model gives the clearest visual mapping?

Answer: A

The V-shaped model pairs specification and design activities with verification and validation activities. The other models emphasize feedback, risk, or iteration rather than that paired test structure.

Question 06Process modelsL03 pp. 18–26

Users cannot describe a form until they see one. A quick mock-up is built solely to discover requirements, then discarded before production construction. Which choice is it?

Answer: B

A throwaway prototype tests understanding and is deliberately discarded. An evolutionary prototype is refined into the product; an increment and a transition phase describe different lifecycle ideas.

Question 07Process modelsL03 pp. 27–33

A safety-critical system faces uncertain technology and costly failure. What makes the spiral model especially suitable?

Answer: B

Risk analysis is explicit in each spiral cycle, followed by development and evaluation. The model is iterative and can use prototypes; stakeholder evaluation remains important.

Question 08Unified ProcessL03 pp. 34–45

In the Unified Process, a team stabilizes the architecture and addresses major technical risks before large-scale construction. Which phase is this?

Answer: B

Elaboration establishes an architectural baseline and tackles significant risks. Inception establishes scope and business case; construction builds the product; transition puts it into users' hands.

Question 09AgileL04 pp. 7–15

A client changes priorities after seeing a working increment. Which response most closely follows the agile principles in the slides?

Answer: B

Agility values collaboration, working software, and response to change. It still requires planning and quality work; the manifesto does not say to eliminate them.

Question 10Agile methodsL04 pp. 22–34

A Scrum team has regular sprint events but integration defects keep accumulating. Which addition directly addresses engineering practice?

Answer: B

Scrum supplies roles and events; XP includes concrete coding practices. More meetings or altered roles do not repair the build and design discipline causing integration defects.

Question 11RequirementsL05 pp. 6–10, 31–32

‘The system shall return search results within two seconds for 95% of requests’ is best classified as what?

Answer: B

It constrains a measurable quality of service, performance, rather than naming a business function. Actors and invariants belong to other modeling levels.

Question 12Requirement qualityL05 pp. 33–35

Which requirement is easiest to verify objectively?

Answer: C

A measurable threshold and stated conditions permit a repeatable check. ‘User friendly,’ ‘very fast,’ and ‘modern’ are ambiguous without criteria.

Question 13Use-case relationshipsL06 pp. 15–18, 30–33

An ATM always completes Transfer Funds, then optionally prints a receipt when the customer chooses it. How should printing be related to transfer?

Answer: B

Optional behavior extends the base Transfer Funds use case. Include means mandatory reused behavior. A standalone Print Receipt association would falsely allow receipt printing outside the transfer flow.

Question 14Use-case boundariesL06 pp. 13–15, 34–37

Couriers physically deliver parcels and update parcel status in the system. Which is a system use case?

Answer: C

A use case describes a system service that benefits an actor. Physical delivery actions occur outside the software boundary; recording status is a system interaction.

Question 15Use-case specificationL06 pp. 36–37, 46–49

A student logs in once and then views several course pages. What is the best way to express authentication for View Course Page?

Answer: B

The prerequisite is an already authenticated session. A mandatory include would imply logging in on every view; username entry is only a step. The precondition records the real rule explicitly.

Question 16DFD notationL07 pp. 8–11, 35–36

Which DFD fragment obeys the basic naming and connection rules?

Answer: B

Processes use action verb phrases, flows use noun labels, and each flow touches a process. Direct entity-to-store transfer, treating an entity as a transform, and two-headed arrows violate the slide rules.

Question 17DFD decompositionL07 pp. 25–37

A parent process receives Application and sends Decision. Its child diagram receives Application but sends only Receipt. What is wrong?

Answer: B

Balancing requires the child's external input and output flows, at the decomposition boundary, to match the parent's. Internal flows may differ; the missing Decision is a boundary mismatch.

Question 18DFD validationL07 pp. 35–38

A DFD has valid symbols and balanced flows, but users say it omits the real approval step. Which validation has failed?

Answer: B

Syntax asks whether notation and structural rules are followed. Semantic validation asks whether the model accurately represents the business process; user walkthroughs reveal the missing approval.

Question 19Class relationshipsL08 pp. 27–30, 43–45

A purchase can have several payments, and each payment has its own date and amount. Where should the payment date and amount go?

Answer: C

Each payment occurrence owns its own date and amount, so Payment is the proper class and is linked to its Purchase. Putting repeated payment facts on Customer or Purchase loses per-payment identity.

Question 20MultiplicityL08 pp. 27–28, 41–42

One lecturer may teach many classes and one class may have several lecturers. Which multiplicities express the stated possibility at both association ends?

Answer: B

A number beside a class says how many instances of that class can be linked to one instance at the opposite end. ‘May’ permits zero; if the case instead requires at least one, use 1..*. The diagram must place multiplicities at the relevant ends.

Question 21Whole-part relationshipsL08 pp. 32–34

A room is modeled as a part whose identity and lifetime depend on its building. Which notation expresses that strong whole-part relationship?

Answer: B

Composition uses a filled diamond at the whole, Building. A hollow diamond means shared aggregation; the other symbols represent inheritance or use-case extension.

Question 22Model consistencyL09 pp. 8–12

A CRC card lists Payment as a collaborator of Purchase, but the class diagram has no relationship between them. What should the walkthrough flag?

Answer: B

Structural V&V checks that CRC responsibilities, attributes, collaborators, and relationships are reflected in the class diagram. The missing link requires investigation; it does not automatically mean the class should be deleted.

Question 23Cohesion and couplingL10 pp. 6–12

Flight stores an airport's name, city, gate policy, and maintenance contact even though Airport already owns those facts. Which change best improves class cohesion without losing the flight's route?

Answer: B

Flight should represent the flight; Airport should own airport facts. Role-labeled departure and arrival links preserve the route while avoiding duplicated unrelated state. Deleting Airport, copying fields, or using global state increases confusion and dependence.

Question 24Contracts and constraintsL10 pp. 38–43

A rental return method requires an active rental, must record the actual return time after success, and must never leave a negative fine. Which labels are correct?

Answer: B

An active rental is required before the method runs, recording return time is the promised result after success, and nonnegative fine is a rule that valid rental objects must always satisfy. A contract documents these obligations for a public method.

Question 25Class and method designL10 pp. 6–18, 19–23, 39–43

Answer: B

The call chain makes Checkout know Sale's internal collaborator. A Sale method can answer the requested amount while containing that collaboration. Public fields and longer chains increase coupling; moving all state ignores responsibility and cohesion.
